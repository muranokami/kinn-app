# 健康管理機能 法務・産業医確認チェックリスト

作成日: 2026-08-28
対象: kinn-app 健康管理機能(体調チェック・健康プロフィール・健康スコア・健康アラート・
勤怠×健康分析・月次健康記録・管理者ダッシュボード)、および今回実装した監査ログ機能

本書はコードではなく、法務・産業医との打ち合わせで確認事項を漏れなく詰めるための
チェックリストです。確認結果を反映するための設定項目(保持期間・通知先・閲覧権限範囲など)は
アプリ側でハードコードせず、設定ファイル(application.properties 等)から変更できる構造に
しています。本書の各項目の結論が出た時点で、該当する設定値・権限モデルを見直してください。

---

## 0. 本ツールの位置づけ(2026-08-29 追記)

**本ツールは、労働安全衛生法上のストレスチェック制度(第66条の10)の代替ではなく、
従業員本人による健康状態の自己記録・セルフケア支援を目的とした機能である。**
最終的な法的性質の確認(下記1.)は別途必要だが、この位置づけに沿って、現在の実装は
以下の設計・運用方針を取っている。

- 体調チェック・健康プロフィールの全項目が任意入力であり(`HealthCheckDto` /
  `HealthProfileDto` のいずれにも必須(`@NotNull`)制約は無く、画面側(health-check.html /
  health-profile.html)にも`required`属性は一切無い)、未入力のままでも保存・利用できる。
- 入力しなくても、勤怠・タスク・スケジュール管理など他の機能の利用に一切支障はない
  (ログイン後のアクセス制御(`SecurityConfig`)は健康データの入力状況を条件にしていない。
  強制的にどこかの画面へ誘導する仕組みも無い)。
- 健康アラート・健康スコアの算出結果は、本人が画面を開いた時にのみその場で表示され、
  上長・人事・産業医等の第三者へ自動的に送信されることは無い(メール・Slack等の外部通知
  機能自体を実装していない。`SecurityConfig`のjavadoc、および下記5.参照)。
- 本人はいつでも、入力した体調チェック・健康プロフィール(・それらから自動生成された
  健康アラート)を削除できる(`HealthSelfDataController` / `DELETE /api/health/self-data`。
  health-profile.html末尾の「健康記録をすべて削除する」ボタン。下記6.参照)。
- 結果を人事評価(evaluation)や就業上の措置の判断材料として直接利用しないことを、
  管理者向けの運用ガイドラインとして明文化する(下記5.)。

## 1. ストレスチェック制度該当性

- [ ] 「今日の体調チェック」「健康プロフィール」「健康スコア」「健康アラート」の取得が、
      労働安全衛生法第66条の10に定める「心理的な負担の程度を把握するための検査」
      (ストレスチェック制度)に該当するか、産業医・社労士に確認する。
  - 該当する場合、以下の法定要件を満たしているか確認する:
    - [ ] 実施者(医師・保健師等の有資格者)が検査の実施・結果の評価を行っているか
          (本機能は現状、システムが機械的にスコアを算出するのみで、有資格者による
          評価を経ていない)。
    - [ ] 実施時期(年1回等の法定頻度)を満たしているか、あるいは毎日のセルフチェックは
          制度上「別物」として整理できるか。
    - [ ] 結果を本人の同意なく事業者(人事等)に提供していないか
          (ストレスチェック制度は、本人同意のない結果の事業者への通知を禁止している)。
    - [ ] 高ストレス者への面接指導の申出勧奨など、法定のフォローアップ体制が必要か。
  - 該当しない(=制度の対象外の任意の健康管理ツールと整理できる)場合も、その根拠を
    文書化し、今後の説明責任に備える。

## 2. 取得同意のタイミング・方法

- [x] **(確認済み・2026-08-29)** 健康情報(体調チェック・健康プロフィール)の入力は
      完全に任意であり、入力しなくても勤怠・タスク等の他機能の利用に支障はない
      (上記0.参照)。したがって「利用規約への同意」と「健康情報の入力そのものへの同意」は
      性質が異なり、後者は各画面への入力操作自体が同意の意思表示として整理できる
      (=強制取得ではない)。ただし下記の論点は引き続き未確認。
- [ ] 従業員からの健康情報取得について、利用規約(アカウント登録自体に必要な同意)を
      いつ・どのように得るか。
  - [ ] 新規登録画面(register.html)での同意取得(チェックボックス等)が必要か。
  - [ ] 同意文言・取得記録(いつ・どのバージョンの説明に同意したか)の保存方法。
  - [ ] 既存ユーザー(施行前に登録済みのユーザー)への遡及的な同意取得をどう行うか。

## 3. 閲覧権限者の範囲・権限モデル

- [ ] 健康データを閲覧できるのは誰か(人事、直属の上長、産業医、システム管理者)を
      具体的に確定する。
- [ ] 現状の権限モデルは `UserRole`(USER / ADMIN の2区分)のみである。
  - [ ] 「健康データは見られるが、従業員の権限変更・削除等の従業員管理はできない」
        といった産業医・保健師向けの中間的な役割(例: `ROLE_HEALTH_STAFF`)が
        必要かどうかを論点として検討する。
  - [ ] 必要と判断された場合、`UserRole` への列挙値追加、および健康関連APIの認可条件の
        見直し(現状 `/api/admin/health/**` は `hasRole("ADMIN")` のみで保護されており、
        「ADMIN=人事権限者」と「健康データ閲覧者」が同一視されている点に注意)。
  - [ ] 直属の上長が部下の個人別データ(集計でなく個人データ)を閲覧できる機能は
        現状存在しない。必要であれば要件化する。

## 4. 管理者ダッシュボードの個人特定リスク

- [ ] 会社・部署単位の集計(平均健康スコア・平均睡眠時間・疲労度・ストレス度・
      アラート件数等)が、間接的にでも個人を特定できてしまう粒度になっていないか。
  - [ ] 部署の人数が少ない場合(例: 1〜2名)、平均値からほぼ個人のデータが
        特定できてしまう懸念がある。最小表示人数の閾値(例: 5名未満の部署は
        集計を表示しない、または上位階層に統合する)を設けるか検討する。
  - [ ] 将来的な部署別集計の粒度細分化(役職別・年齢層別等)を行う場合も、
        同様の再特定リスクを毎回確認する運用ルールを定める。
  - [ ] 現行実装(`AdminHealthController` / `AdminHealthService`)は個人の健康値そのものは
        返さない設計だが、上記の「少人数部署での事実上の個人特定」は集計方式だけでは
        防げないため、運用ルール(閾値)側での対応が必須になる見込み。

## 5. 健康アラートの通知先・不利益取り扱いの防止

- [ ] 健康アラートの通知先は本人のみか、上長・産業医にも通知するか。
  - [ ] 現行実装は本人が画面を開いた時にのみアラートが表示される(プッシュ通知等の
        第三者への自動送信は行っていない)。この前提を維持するか、通知機能を
        追加するかを確認する。
  - [ ] 上長・産業医への通知を追加する場合、通知先を設定ファイルで変更可能にする
        (コードにメールアドレス等をハードコードしない)。
- [ ] アラート(体調不良の兆候等)を理由に、配置転換・評価低下・不利益な取り扱いを
      行わないことを、就業規則・運用ガイドラインで明文化する。
- [ ] 産業医面談の要否判断とアラートの関係(アラート=即面談ではないことの周知)。
- [ ] 健康アラート・健康スコアの結果を、会社が人事評価(evaluation)や就業上の措置の
      判断材料として直接利用しないことを、管理者向けドキュメント・運用ガイドラインに
      明記する(上記0.で位置づけとしては明記済みだが、社内向けの正式なガイドライン文書
      への反映は別途必要)。

## 6. 監査ログの保持期間・開示請求への対応フロー

- [ ] 監査ログ(health_audit_log)の保持期間を確定する。
  - 現行実装は `application.properties` の `app.audit.health.retention-days`
    (暫定値: 365日)で管理しており、コードの変更なしに値を見直せる。
  - [ ] 法定・社内規定上、適切な保持期間(例: 1年、3年、5年)を確定する。
  - [ ] 保持期間経過後の自動削除バッチは今回未実装(将来追加できる構造にとどめている)。
        削除バッチをいつまでに実装するかを決める。
- [ ] 本人から「誰が自分のデータを見たか確認したい」という開示請求があった場合の対応フロー。
  - 現行実装では、一般ユーザーは `/api/health/audit-log`(自分専用ログ閲覧画面)で
    自分自身のデータへのアクセス履歴をセルフサービスで確認できる。
  - [ ] このセルフサービス画面で開示請求への対応が十分か、それとも別途正式な開示請求
        窓口(書面等)を用意する必要があるかを確認する。
  - [ ] 個人情報保護法上の「保有個人データの開示請求」に監査ログ自体が該当するかどうかも
        論点(監査ログはアクセス記録であり、開示対象の性質を法務に確認する)。
- [x] **(2026-08-29 対応済み)** 本人から「自分の健康データを削除してほしい」という
      削除申請があった場合の技術的な対応フロー。
  - **誰が**: 本人のみ(自分自身のデータに限る。管理者による代行削除は現時点では未実装
    ・未対応 — 必要になった場合は別途、管理者操作の監査ログと合わせて設計すること)。
  - **どの画面/API**: `health-profile.html`末尾の「健康記録をすべて削除する」ボタン
    (`DELETE /api/health/self-data`、`HealthSelfDataController` /
    `HealthSelfDataDeletionService`)。確認ダイアログを経てから実行する。
  - **削除範囲**: 健康プロフィール(`health_profile`)・体調チェックの全履歴
    (`health_check`)・それらから自動生成された健康アラート(`health_alert`)。
  - **削除範囲外**: 従来の月次健康記録(`health_record`。1日単位の削除は既存の
    `HealthController`にあり)、食事記録・レシピ等の他機能のデータ、監査ログ自体
    (`health_audit_log`。削除操作そのものも監査ログに記録される。保持期間は上記の
    論点のまま)。
  - [ ] 法務確認前でも技術的な削除手段は用意した、という位置づけであり、削除範囲
        (特に月次健康記録・食事記録を含めるべきか)や、退職者データとの関係(下記7.)は
        引き続き法務確認が必要。

## 7. 退職者の健康データ・監査ログの保持期間と削除方針

- [ ] 退職者の健康データ(health_profile, health_check, health_record 等)を

- [ ] 退職者に関する監査ログ(health_audit_log)をいつまで保持するか

- [ ] 労働基準法上の記録保存義務がある情報(該当する場合)との整理。

## 8. データの保存場所・バックアップ・第三者提供

- [ ] 健康データ・監査ログの保存場所(現状は自社(想定)運用のPostgreSQLデータベースのみ。
      クラウド事業者を利用する場合はそのリージョン・事業者名を確認)。
- [ ] バックアップの取得方法・保存期間・アクセス権限者。
- [ ] 健康データ・監査ログを社外の第三者(クラウドベンダーのサポート、外部の分析ベンダー等)
      へ提供することがあるか。ないのであれば「社内利用に閉じる」旨を文書化する。
  - [x] AI献立提案機能(下記9.)は外部APIへデータを送信する。健康プロフィール・体調チェック・
        健康スコアの値は送信対象から除外済み(2026-08-29対応、下記9.参照)。ただし食の好み
        (アレルギー等)・前日の食事内容の要約は引き続き送信しているため、これらが
        「要配慮個人情報」に該当しないかは下記9.の未確認事項として残っている。

## 9. 食事記録・レシピ機能で扱う情報の要配慮個人情報該当性

- [x] **(2026-08-29 対応済み)** 外部AI API(Anthropic API)への送信内容から、身長・体重・BMI・
      平均睡眠時間・平均運動時間・直近の睡眠/疲労度/ストレス度・健康スコアといった
      健康プロフィール・体調チェック・健康スコアの値を除外した(セキュリティレビュー指摘を受けての対応。
      `MealRecommendationService#buildPrompt`参照)。これらの値は現在、外部へは一切送信せず、
      サーバー内部のルールベース提案ロジック(`analyzeGaps`)でのみ利用している。
  - [x] 一方、アレルギー・食事制限・好き嫌い・予算・調理時間といった「食の好み」
        (user_food_preference)は、引き続き外部AI APIへ送信する方針とした。
        アレルギー食材を誤って提案しないための安全上の理由による判断で、実際にAIの提案結果に
        アレルギー食材が含まれてしまった場合も、サーバー側(`safeAiOrFallback`)で二重に検知し、
        安全なルールベースの代替案へ自動的に差し替える仕組みがある。
  - [ ] 上記の対応を踏まえてもなお、食の好み(特にアレルギー情報)自体が「要配慮個人情報」に
        該当するかは未確認のまま。該当する場合、外部送信について本人への説明
        (プライバシーポリシー等)が必要かどうかを法務に確認する。
  - [ ] 食事記録(meal_record)自体(何を食べたか)が、健康情報と同様に
        個人情報保護法上の「要配慮個人情報」に該当しないかも別途確認する
        (この情報は現状、外部AI APIへも要約された形で送信している。buildPrompt参照)。
  - [ ] 該当する場合、取得同意(2.)・保存期間(6./7.)・閲覧権限(3.)の各論点を
        食事関連情報にも同様に適用する。

## 反映方法についてのメモ(エンジニア向け)

上記の確認結果を反映する際、以下の設定項目は既にコードから切り出し済みです
(値の変更のみで対応可能):

- 監査ログ保持期間: `application.properties` の `app.audit.health.retention-days`

2026-08-29時点で実装済みのもの(セキュリティレビュー4-4対応):

- 本人による健康記録(プロフィール・体調チェック・アラート)の自己削除機能
  (`HealthSelfDataController` / `HealthSelfDataDeletionService`、
  health-profile.htmlの「健康記録をすべて削除する」ボタン。上記6.参照)
- 体調チェック・健康プロフィールの全項目が任意入力であることの確認・維持
  (必須バリデーションを追加しないことの確認。上記0.参照)
- 本人以外への健康アラート・健康スコアの自動通知を行わない設計の維持
  (メール/Slack等の外部通知機能自体を実装していないことの再確認。上記0./5.参照)

以下は今回のスコープでは実装しておらず、確認結果に応じて追加実装が必要です:

- 保持期間経過後の自動削除バッチ
- アラートの上長・産業医への通知機能、および通知先の設定項目化
- 「健康データ閲覧者(産業医等)」のための中間的な権限ロールの追加
- 部署別集計の最小表示人数閾値による個人特定防止ガード
- 管理者による代行削除(本人以外からの削除申請への対応が必要になった場合)
- 月次健康記録(health_record)・食事記録を含めた削除範囲の拡張(法務確認後に検討)
