# 健康管理機能 法務・産業医確認チェックリスト

作成日: 2026-08-28
対象: kinn-app 健康管理機能(体調チェック・健康プロフィール・健康スコア・健康アラート・
勤怠×健康分析・月次健康記録・管理者ダッシュボード)、および今回実装した監査ログ機能

本書はコードではなく、法務・産業医との打ち合わせで確認事項を漏れなく詰めるための
チェックリストです。確認結果を反映するための設定項目(保持期間・通知先・閲覧権限範囲など)は
アプリ側でハードコードせず、設定ファイル(application.properties 等)から変更できる構造に
しています。本書の各項目の結論が出た時点で、該当する設定値・権限モデルを見直してください。

## 現在の開発段階について(2026-08-30 追記)

現時点(本追記時点)では、本アプリは個人開発段階であり、開発者本人以外の第三者(他社・他人)の
従業員データを実際に扱う運用は行っていない。個人情報保護法は法人か個人事業主かを区別せず、
「事業として他人の個人情報を扱う者」に適用されるため、**将来的に他社・他人へ実際に提供・運用を
開始する場合は、その時点で本書の未確認事項([ ]の項目)を確認する必要がある。**

そのため本書の各項目は、「今すぐ確認が必要」なものではなく、**実際の提供・運用を開始する前に
確認すべき事項**という位置づけに整理している。現時点で確認が完了していないこと自体は、
現在の開発段階(第三者データを扱っていない)においては問題にならない。

## 0. 本ツールの位置づけ(2026-08-29 追記、2026-08-29 ストレス関連機能撤廃を反映)

**本ツールは、労働安全衛生法上のストレスチェック制度(第66条の10)の代替ではなく、
従業員本人による健康状態の自己記録・セルフケア支援を目的とした機能である。**
この位置づけに沿って、現在の実装は以下の設計・運用方針を取っている。

- **「心理的な負担の程度」を測定・表示・アラート・集計する機能を、アプリから完全に
  削除した**(下記1.参照)。ストレス度の入力欄・健康スコアの構成要素・健康アラートの
  種別・勤怠×健康分析の相関表示・管理者ダッシュボードの部署別平均のいずれからも、
  「ストレス」に関する測定値は一切出力されない。
- 体調チェック・健康プロフィールの残りの全項目(体調・睡眠・疲労度・運動・体温等)も
  任意入力であり(`HealthCheckDto` / `HealthProfileDto` のいずれにも必須(`@NotNull`)
  制約は無く、画面側(health-check.html / health-profile.html)にも`required`属性は
  一切無い)、未入力のままでも保存・利用できる。
- 入力しなくても、勤怠・タスク・スケジュール管理など他の機能の利用に一切支障はない
  (ログイン後のアクセス制御(`SecurityConfig`)は健康データの入力状況を条件にしていない。
  強制的にどこかの画面へ誘導する仕組みも無い)。
- 健康アラート・健康スコアの算出結果は、本人が画面を開いた時にのみその場で表示され、
  上長・人事・産業医等の第三者へ自動的に送信されることは無い(メール・Slack等の外部通知
  機能自体を実装していない。`SecurityConfig`のjavadoc、および下記5.参照)。
- 本人はいつでも、入力した体調チェック・健康プロフィール(・それらから自動生成された
  健康アラート)を削除できる(`HealthSelfDataController` / `DELETE /api/health/self-data`。
  health-profile.html末尾の「健康記録をすべて削除する」ボタン。下記6.参照)。
- 結果を人事評価(evaluation)や就業上の措置の判断材料として直接利用しないことを、
  管理者向けの運用ガイドラインとして明文化する(下記5.)。

## 1. ストレスチェック制度該当性

- [x] **(2026-08-29 対応済み)** 労働安全衛生法第66条の10のストレスチェック制度は、
      「心理的な負担の程度を把握するための検査」を対象とする制度である。本アプリからは
      「ストレス度」の入力・表示・アラート・集計を行う機能を完全に削除したため
      (以下、具体的な削除箇所)、**現状、この制度の対象となりうる「心理的な負担の程度を
      把握するための検査」に該当する機能自体がアプリ内に存在しない。**
  - 削除した箇所: `health_check.stress_level`(今日の体調チェックのストレス度入力)、
    `health_profile.stress_level`(健康プロフィールの普段のストレス度)、
    `HealthAlertType.HIGH_STRESS`(「ストレスが高い状態の継続」アラート、新規生成は停止。
    過去に生成された行はV2マイグレーションで削除済み)、健康スコアの構成要素、
    勤怠×健康分析の「残業時間とストレス度」相関表示、管理者ダッシュボードの
    部署別「平均ストレス度」集計。
  - 残っている体調チェック項目(体調・睡眠・疲労度・運動・体温)は、いずれも
    「心理的な負担の程度」を対象とした検査ではなく、一般的な生活習慣の自己記録である。
  - [ ] とはいえ、これは実装上の対応であり、最終的な法的性質の確認(産業医・社労士への
        確認)そのものを完全に不要にするものではない。特に「体調(condition)」項目が
        間接的に心理状態を含意しないか、「健康スコア」という総合評価値の出し方自体が
        別の法規制に抵触しないか等、念のため確認しておくことを推奨する
        (ただし対応前と比べて、確認すべき論点・リスクは大幅に縮小している)。

## 9. 食事記録・レシピ機能で扱う情報の要配慮個人情報該当性

- [x] **(2026-08-29 対応済み)** 外部AI API(Anthropic API)への送信内容から、身長・体重・BMI・
      平均睡眠時間・平均運動時間・直近の睡眠/疲労度/ストレス度・健康スコアといった
      健康プロフィール・体調チェック・健康スコアの値を除外した(セキュリティレビュー指摘を受けての対応。
      `MealRecommendationService#buildPrompt`参照)。これらの値は現在、外部へは一切送信せず、
      サーバー内部のルールベース提案ロジック(`analyzeGaps`)でのみ利用している。
  - [x] 一方、アレルギー・食事制限・好き嫌い・予算・調理時間といった「食の好み」
        (user_food_preference)は、引き続き外部AI APIへ送信する方針とした。
        アレルギー食材を誤って提案しないための安全上の理由による判断で、実際にAIの提案結果に
        アレルギー食材が含まれてしまった場合も、サーバー側(`safeAiOrFallback`)で二重に検知し、
        安全なルールベースの代替案へ自動的に差し替える仕組みがある。
  - [ ] 上記の対応を踏まえてもなお、食の好み(特にアレルギー情報)自体が「要配慮個人情報」に
        該当するかは未確認のまま。該当する場合、外部送信について本人への説明
        (プライバシーポリシー等)が必要かどうかを法務に確認する。
  - [ ] 食事記録(meal_record)自体(何を食べたか)が、健康情報と同様に
        個人情報保護法上の「要配慮個人情報」に該当しないかも別途確認する
        (この情報は現状、外部AI APIへも要約された形で送信している。buildPrompt参照)。
  - [ ] 該当する場合、取得同意(2.)・保存期間(6./7.)・閲覧権限(3.)の各論点を
        食事関連情報にも同様に適用する。

## 10. 健康管理データの保存時暗号化(2026-08-30 追記、法務・情報セキュリティ確認事項)

本項目はエンジニア側の実装事実の記録であり、これによって個人情報保護法上の安全管理措置義務
(法第23条)を満たすと判断・確定させるものではない。十分性の評価・要否の判断はあくまで
法務側の確認事項として下記に残す。

- [x] **(実装済み・2026-08-30)** 健康管理データ(身長・体重・血圧・体温・睡眠時間・疲労度・
      運動時間・歩数・喫煙/飲酒状況・体調・メモ。`health_profile` / `health_record` /
      `health_check`)について、DB保存前にアプリ層でAES-256-GCMによる暗号化を行うように
      実装した(`HealthDataEncryptor` / JPAの`AttributeConverter`。既存データも起動時の
      移行処理で暗号化済み)。鍵は環境変数`APP_HEALTH_ENCRYPTION_KEY`から取得する
      (README「健康管理データの保存時暗号化」参照)。
- [x] **(実装済み・2026-08-30 追加分)** 健康アラートの種別・深刻度・メッセージ
      (`health_alert`)、および食の好み・アレルギー・食事制限(`user_food_preference`の
      `favorite_foods`/`disliked_foods`/`allergies`/`dietary_restrictions`)も同じ方式で
      暗号化した。特にアレルギー・食事制限は上記9.で「要配慮個人情報への該当が未確認」と
      記録している情報そのものであり、該当性の法務判断を待たずに技術的な保護のみ先行して
      実施した位置づけ(該当しないと判断された場合でも、暗号化していること自体が
      デメリットにはならない前提)。
- [ ] 上記の暗号化対応が、要配慮個人情報に対する安全管理措置として十分かどうかの評価
      (暗号方式・適用範囲・鍵管理方法を含む)を法務に確認する。
- [ ] 暗号化鍵の管理方法(発行・保管・アクセス権限者・ローテーション方針)を、社内の
      情報セキュリティ規程と整合させる。現行実装は環境変数からの注入のみで、鍵管理システム
      (KMS等)の利用や鍵のローテーション手段は用意していない。本番運用開始前に、鍵が
      開発用の既定値のままになっていないかを確認する運用チェックを、関連部門と共有すること。
- [ ] 万一データが漏えいした場合、暗号化されていた事実が個人情報保護法上の報告義務
      (法第26条。要配慮個人情報は原則報告対象)の要否判断にどう影響するか
      (暗号化鍵自体が漏えいしていない場合の扱い等)を法務に確認する。

- 健康管理データの暗号化鍵: `application.properties` の
  `app.security.health-encryption.key`(環境変数 `APP_HEALTH_ENCRYPTION_KEY`)

2026-08-29時点で実装済みのもの(セキュリティレビュー4-4対応):

- 本人による健康記録(プロフィール・体調チェック・アラート)の自己削除機能
  (`HealthSelfDataController` / `HealthSelfDataDeletionService`、
  health-profile.htmlの「健康記録をすべて削除する」ボタン。上記6.参照)

- 本人以外への健康アラート・健康スコアの自動通知を行わない設計の維持
  (メール/Slack等の外部通知機能自体を実装していないことの再確認。上記0./5.参照)

十分性の評価は法務確認待ち):
